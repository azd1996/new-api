# 性能保护拒绝日志

性能监控启用并因 CPU、内存或磁盘阈值拒绝请求时，写入现有错误日志（类型 `5`）。保持原有鉴权前保护顺序、阈值判断与 HTTP 503 响应，不读取请求体、不选择渠道、不调用上游、不扣费。

- 遵循现有 `ErrorLogEnabled` 开关。开启时每次拒绝同步尝试写入一条日志，不采样、不限频；数据库故障时不保证落库。高频拒绝会增加日志写入压力，尤其需关注磁盘超限场景。
- 鉴权尚未执行，因此用户、令牌、渠道 ID 为 `0`，名称、模型和分组为空；不从客户端传入的身份或模型字段猜测归属，也不记录请求头、请求体或 URL 查询参数。
- request_id 复用入口生成的请求 ID。管理员可在使用日志的错误类型中按请求 ID、错误内容检索；这些日志没有普通用户归属。
- Content 保留实际使用率和阈值；`other.error_code` 为 `system_cpu_overloaded`、`system_memory_overloaded` 或 `system_disk_overloaded`，`other.status_code=503`，`other.request_path` 为请求路径。
- `other.admin_info.node_name` 记录实例；`other.admin_info.system_overload` 记录本次判断的 CPU/内存/磁盘使用率与阈值，以及 `authenticated=false`。
- 错误签名基于稳定错误码，不带实时使用率或阈值；签名哈希按已有规则同时写入真列和 other，可用于明细错误聚合。Prometheus 错误指标沿用现有开关，无鉴权或渠道信息的维度留空。

仅覆盖原本挂载 `SystemPerformanceCheck` 的路由，不扩大到其他路由。它记录的是网关入口拒绝，不代表上游渠道失败，也不会触发渠道禁用、重试或结算。

## 渠道关联边界与最终决策

当前执行顺序为：性能检查 → 鉴权 → 渠道选择 → 上游调用。超限时在第一步直接返回，因此这里的 503 是本节点返回的，不是某个上游渠道返回的；既没有实际上游渠道，也不能准确推断原本会选中哪个渠道。

- `channel_id=0` 表示尚未选择渠道，不是渠道字段漏记，也不应据此统计某个上游渠道的 503。
- 实际调用上游后出现的 503，仍从正常调用链的渠道错误日志查询，按其中的渠道信息归属。
- 当前日志用于按节点、请求 ID、资源类型分析入口过载拒绝，不能用于分析各渠道受影响的请求数量。
- 若未来需要记录“本来会调用哪个渠道”，必须先执行鉴权和渠道选择，再做过载判断；即使如此，也只能表示选中但未调用的渠道，不能标记成上游实际失败。

2026-10-26 确认：保留方案 A，接受无法关联渠道的边界，不为丰富日志后移性能检查、不增加鉴权或渠道选择开销、不猜测渠道归属。
