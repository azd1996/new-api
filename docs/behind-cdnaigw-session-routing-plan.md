### 当前请求的实际顺序

普通 Claude `/v1/messages` 且 Content-Type 以 `application/json` 开头、需要自动选渠道的请求：

```text
鉴权、解析原始路由模型
  → 冻结原始 affinity 输入并匹配一次
  → 缺少客户端 user_id 时预生成 fallback 候选到 context，原始 body 不变
  → 检查显式指定渠道，或在首次选择时查询原有 affinity 绑定
  → 指定渠道和已有绑定仍需通过分流过滤
  → 无可用绑定时，按实际分组、客户模型前缀开关、分组开关和非标渠道可用性选池
  → 装载选中渠道配置
  → relay 转换请求，按实际分组/outbound model 决定是否注入 prepared fallback
  → 后续参数/retry 改写，发送上游
  → 成功且存在 affinity 绑定上下文时，记录或刷新绑定
```

其他入口在首次调用 affinity matcher 时惰性建立原始匹配快照，不能将上述 Claude 提前准备步骤描述为全部协议入口都已接入。

分流仅对实际组名以 `behind-cdnaigw_` 开头的候选组生效；`auto` 按各实际候选组判断。客户配置按模型前缀匹配、最长前缀优先，未命中默认关闭；但当前代码只对成功解码 trace tag 的客户执行该关闭检查，未解码客户不会进入此显式关闭分支。

在进入分流判断时，原始规则提取不到有效 key 即为非标。分组关闭、客户规则关闭或没有支持当前模型的已启用非标渠道，会使请求走标准池；这只改变候选范围，不将原始非标请求重新分类为标准。

## 目标与结构

维持“一个网关 API Key → 一个分组”，将同一真实上游拆成两个逻辑渠道：

```text
API Key：behind-cdnaigw_部门A
└── 分组：behind-cdnaigw_部门A
    ├── behind-cdnaigw_部门A
    └── behind-cdnaigw_部门A-非标
```

渠道分别维护上游转发配置。客户端继续使用原 Key，无须改变分组或请求模型名。

当前 behind 专用复制校验完整名不超过 50 个 UTF-8 字节。这是该流程的业务限制，不是已经证实的渠道名统一数据库上限。`-非标` 占 7 字节，原名称最多 50 字节时，非标副本最多 57 字节。

### 请求分类

采用相对通用的会话亲和性规则作为分类依据，不硬编码 Claude 或 OpenAI 特定字段：

1. 满足规则的模型、路径、User-Agent 条件。
2. 从规则配置的来源中提取到非空亲和键。
3. 通过规则的值校验。

三者满足即为标准请求，否则为非标请求。沿用现有规则顺序及键来源顺序。

“匹配规则”与“亲和缓存命中”必须分开：新会话、缓存过期、缓存查询失败均不应改变请求分类。不得以 `GetPreferredChannelByAffinity` 返回的缓存命中布尔值作为分类结果。

分类基于选渠道前的客户端原始请求。后续网关补全会话字段、参数覆盖、重试改写均不重新分类。

当前默认 Claude 亲和规则只要求 `metadata.user_id` 非空，不校验内部 `session_id`；因此按本方案，“标准”表示符合配置规则，不额外承诺协议格式、会话唯一性或缓存命中效果。

### 分组开关与存量兼容

分流是分组级配置，仅适用于名称以 `behind-cdnaigw_` 开头的实际分组。其他分组保持原有路由行为，不按本方案过滤渠道。

默认采用自动模式：按“实际分组 + 当前请求模型”判断，存在处于非禁用状态、支持该模型的非标渠道时自动分流，除非管理员显式关闭。未配置开关等同于自动模式，不需要迁移存量配置。显式允许分流也不强制要求非标渠道存在。

**没有对应模型的非标渠道，或对应非标渠道全部被禁用时，两类请求都走标准渠道。** 不要求存量分组预先创建副本。非禁用状态的精确枚举应在实施时按现有渠道状态定义核对，包括人工和自动禁用。

| 分组配置 | 当前模型存在非禁用非标渠道 | 请求分类 | 首次渠道范围 |
| --- | --- | --- | --- |
| 显式关闭 | 任意 | 任意 | 标准渠道 |
| 默认自动 / 允许分流 | 否 | 任意 | 标准渠道 |
| 默认自动 / 允许分流 | 是 | 标准 | 标准渠道 |
| 默认自动 / 允许分流 | 是 | 非标 | 非标渠道 |

渠道类别按名称末尾精确的 `-非标` 识别，与模型名无关。关闭开关只过滤本分组的候选集，不修改渠道启用状态。

存在非禁用非标渠道并不代表上游调用一定成功。上游失败后的标准渠道回退只能发生在现有策略允许的重试中，不能把故障检测包装成首次选择兜底。

### 非标失败与重试

- 非标渠道已禁用：选渠道时忽略；若该模型没有其他非禁用非标渠道，首次请求直接走标准渠道，不消耗重试次数。
- 非标渠道访问失败，例如异常 HTTP 状态码：由现有逻辑判断是否可重试，不因本功能新增或强制重试。
- 重试次数为 0：返回原有处理结果，不额外请求标准渠道。
- 存在剩余重试次数且现有策略允许换渠道重试：允许选择同组标准渠道，标准渠道不得被首次分流过滤器永久排除。
- 同渠道 retry override、不可重试错误、请求已无法重放等限制继续遵守现有语义；重试次数大于 0 本身不保证一定重试或一定切到标准渠道。
- 请求分类始终保持非标；重试进入标准渠道只改变本次尝试的候选范围，不把请求重新归为标准。

匹配步骤不查亲和缓存，不执行参数模板，不设置严格绑定策略。原有亲和逻辑继续负责策略、缓存查询、绑定使用与回写。

### 选渠道时机

以下为基础分流流程；完整黏滞优先的目标顺序见“黏滞优先与分流身份”，当前实际顺序见文首。

```text
鉴权、读取原始请求模型
  → 共享规则匹配，固定请求分类
  → 确定实际候选分组及其分流策略
  → 按当前模型和非标渠道禁用状态形成首次渠道候选范围
  → 校验历史亲和绑定，或按现有优先级、权重选择
  → 装载渠道配置
  → 协议处理、参数覆盖、会话补全
  → 转发上游
```

沿用现有渠道约束机制，不在选中渠道、装载配置后替换渠道 ID，避免密钥、代理、参数覆盖与最终渠道不一致。

固定分组、auto 实际候选组、亲和命中、普通重试、同渠道 retry override 均须遵守同一策略。auto 场景按实际候选组读取配置，不能把 `auto` 当成实际组，也不能仅根据渠道所属组列表判断。

请求分类和分组配置采用一次请求内一致的快照。候选渠道仍遵守现有状态检查，不能因为快照继续选择已禁用渠道。重试时按上述规则允许进入标准渠道；这是明确的重试阶段行为，不是重新分类。

### 请求体与特殊传输

- 复用现有可重放 body storage，避免重复读取或重复物化大请求体。
- 请求体读取失败与字段不存在必须区分，不应把读取异常静默当成非标。
- WebSocket 应在取得首个请求信息且选渠道前分类；不得因为升级握手没有 JSON body 就直接归为非标。
- 只依赖选渠道前可用的上下文来源；依赖选中渠道后才出现的字段会产生循环依赖，需要配置提示。

### 黏滞优先与分流身份

会话黏滞和会话分流是两个独立的决策维度：

- 会话黏滞决定是否优先复用已经绑定的物理渠道；
- 会话分流只在没有可用黏滞记录时生效，决定请求进入标准渠道池还是非标准渠道池。

渠道选择顺序固定为：

```text
确定本次请求的标准/非标准类别
  → 生成用于黏滞的有效 key
  → 使用「key + is_nonstandard」查询黏滞
  → 命中有效绑定：优先使用绑定渠道
  → 未命中或绑定失效：按固定类别选择标准/非标准渠道池
  → 成功后使用同一组合写入或刷新黏滞
```

默认 Claude affinity 规则使用客户端原始请求中的 `metadata.user_id`：

```text
原始 affinity key 存在    → 标准请求，is_nonstandard = 0
原始 affinity key 不存在  → 非标请求，is_nonstandard = 1
```

原始请求没有 `metadata.user_id` 时，仍然先按非标请求处理；但非标请求需要通过内容和请求上下文生成稳定的 fallback key，并使用该 key 建立和复用非标会话的黏滞。这个 fallback key 必须在选渠道前生成，并由渠道选择和 relay 全链路复用同一个值。

黏滞身份采用组合字段：

```text
affinity identity = key + is_nonstandard
```

建议缓存索引至少包含：

```text
group
model
rule
is_nonstandard
key
→ channel_id
```

`is_nonstandard` 表示本次会话确定的分流类别，不表示实际最后使用的物理渠道。非标请求重试时回退到标准渠道，仍然保持 `is_nonstandard = 1`，不能因为实际渠道来自标准池而改写为标准会话。

没有可用黏滞记录的新请求按类别进入对应渠道池，渠道成功后用同一个组合建立黏滞。后续请求只要生成相同的 fallback key，就应优先复用原绑定渠道。

现有 strict 亲和会在历史渠道不满足过滤条件时返回 `strict_session_binding_unavailable`。

区分两类原因：

- 分流策略或分类规则改变，使历史绑定属于错误类别：使旧绑定失效，在新候选范围重新绑定。标准和非标绑定通过 `is_nonstandard` 隔离，不能因 key 相同而互相覆盖。
- 渠道故障或其他原有失效条件：保留原有 strict 行为，不因为本功能绕过禁止重试的策略。
- 非标渠道被禁用使自动分流不再生效：按分流策略变化处理，允许进入标准候选范围，不被旧类别绑定阻断；其他渠道禁用情形仍遵守原有 strict 语义。

重新绑定可能影响上游缓存及会话连续性，不能保证无损切换。

### 黏滞失效与重试

绑定渠道不存在、被禁用或不再满足当前渠道选择条件时，按本次请求已经固定的 `is_nonstandard` 重新选择渠道池。重试期间不得重新计算请求类别。

非标请求允许回退标准渠道时，只允许单向迁移：

```text
非标池 → 标准池
```

进入标准回退阶段后，本次请求剩余重试不得再次回到非标池。分组不允许重试时，首个渠道失败后直接返回失败，不得通过切换渠道绕过该限制。

一次请求的黏滞身份在重试期间保持不变：

```text
初始身份：fallback-key + is_nonstandard=1
非标渠道失败并回退标准渠道
最终身份：fallback-key + is_nonstandard=1
```

## 已确认的五项边界

### 1. “没有非标渠道”的判断范围

按“实际分组 + 当前请求模型”判断，并结合边界 2、5，只统计非禁用非标渠道。仅给 Claude 配置非标渠道时，其他未覆盖模型仍走标准渠道。

### 2. 已配置非标渠道但不可用时是否回退

禁用时忽略非标渠道，没有其他对应非标渠道则直接走标准渠道。上游故障时不增加额外尝试：重试次数为 0 不切换；有剩余次数且现有策略允许换渠道重试时，可以重试标准渠道。

### 3. 亲和绑定开关是否影响分类

只复用规则，不受绑定总开关及 `SessionMode=off` 影响。关闭会话粘性不改变流量类别。

### 4. strict 旧绑定与显式指定渠道

分流策略变更导致的旧绑定冲突允许重新绑定；显式指定渠道仍校验分流条件，不匹配时报错，不静默改派。渠道测试等管理操作是否豁免，应在实施时核对其入口后明确，不能使管理测试意外转发到另一渠道。

### 5. 功能适用范围

仅限名称以 `behind-cdnaigw_` 开头的分组。默认自动，在当前模型存在非禁用非标渠道时生效，除非显式关闭。其他分组继续现有行为。
