# 骨架前缀 metadata 注入

## 目标

new-api 上游的部分网关只支持通过 `metadata.user_id` 做会话粘滞，不能理解 new-api 自己的请求骨架。因此由 new-api 根据请求骨架和缓存结果维护本机的骨架前缀身份，再通过稳定的骨架哈希完善 `metadata.user_id.session_id`，让上游网关尽量把具有相同缓存前缀的请求视为同一会话。

该机制优化的是上游已有会话粘滞能力下的缓存命中，不负责在 new-api 这一层进行渠道路由，也不是恢复客户端缺失的真实会话身份。

## 两层关系

`h7_C` 只是本机分析或记录时的描述，表示：

```text
骨架前缀 h7 -> 本机观测到的缓存关系 C
```

它不是外发给上游的 session ID。实际请求仍注入：

```text
metadata.user_id.session_id = h7
```

但当前方案的核心并不是根据 `h7` 选择渠道，而是根据当前请求能复用的最长骨架前缀确定应注入的上游会话身份：

```text
本机缓存关系：h7 -> 渠道 C（仅用于记录、分析或结果归因）
上游请求身份：session_id = h7
```

渠道从 A 切换到 C 时，注入值仍由骨架前缀决定，不应因为渠道变化而把内容哈希改成另一个值。渠道选择和重试继续使用现有逻辑。

## 注入模型

假设请求骨架线性增长：

```text
请求1：长度3，按现有逻辑发送，注入 h3
        成功后记录本次结果与 h3 的关系

请求2：长度3，但内容不同，按现有逻辑发送，注入 h3'
        成功后记录本次结果与 h3' 的关系

请求3：长度7，前3与请求1相同
        最长匹配为 h3，注入 h3
        如果发生重试，仍沿用本次选定的注入值
        成功后记录本次结果与相关前缀的关系

请求4：长度9，前7与请求3相同
        最长匹配为 h7，注入 h7
        如果形成新的缓存前缀，追加记录 h9 与本次结果的关系
```

请求时选择的是当前请求能够匹配到的最长、有效且有缓存证据的历史前缀，并将该前缀哈希作为 `metadata.user_id.session_id`。这一步只决定注入值，不改变渠道选择。

因此，请求4在已有 `h7`、尚无 `h9` 记录时，应注入 `h7`，而不是因为请求长度变成9就立即注入 `h9`。`h7` 用于延续已有的上游会话身份，`h9` 用于记录本次请求可能新建的缓存前缀。

## 缓存位置与隔离域

本机观测关系可以抽象为：

```text
骨架前缀 -> 本次请求使用的缓存位置
```

更完整的关系是：

```text
骨架前缀
    -> 缓存隔离域
    -> 本次实际使用的渠道
    -> 渠道 key 或 AWS 账号范围
```

不同 AWS Account 的 Bedrock prompt cache 不能互相访问。因此如果同一个渠道内部存在多个 AWS 账号或 key，单独记录渠道 ID 不足以解释缓存结果。实际使用的 key 或账号范围应作为缓存位置的一部分。

建议记录的逻辑字段包括：

```text
prefix_hash
provider
region
model
channel_id（仅用于结果归因，不用于本方案选路）
key_index 或 account_scope
evidence
confidence
expires_at
```

账号标识如果不应直接暴露，可以保存稳定的内部范围哈希。

## 多断点处理

如果一次请求存在多个缓存断点，例如 `h3` 和 `h7`，应在有足够证据时分别记录：

```text
h3 -> C
h7 -> C
```

但不能仅因为响应存在累计的 cache write 数值，就无条件推断所有断点都已创建。只有上游返回能够对应到具体断点的读写信息时，才能精确标记每个前缀；如果只能得到总的 `cacheReadInputTokens` / `cacheWriteInputTokens`，应只记录能够可靠推导的前缀，并保留证据等级。

## Claude Prompt Cache 语义

以下规则依据 Anthropic Prompt Caching 文档整理。这里的“长度”应理解为 content block 的位置，不是字符数或 token 数。

### 缓存写入是完整前缀

在某个 block 设置 `cache_control` 时，写入的是请求开头到该断点的完整前缀：

```text
断点 block 100
缓存内容 = block 1 ... block 100
```

断点之后的内容不属于该缓存。多个断点分别对应多个累计前缀，例如 block 50 和 block 200 对应：

```text
缓存 A = block 1 ... block 50
缓存 B = block 1 ... block 200
```

它们不是彼此独立的区间缓存。

### 缓存读取依赖检查点

当前请求没有显式断点，且没有启用自动缓存时，不会主动读取历史 Prompt Cache。历史请求写过缓存也不会使没有检查点的请求自动命中。

启用自动缓存时，系统会自动选择一个可缓存位置作为检查点；此时虽然客户端没有手写 `cache_control`，但语义上仍然存在一个缓存检查点。

### 回溯范围

对每个缓存检查点，Claude 最多向前检查 20 个 block 位置，且当前检查点本身计为第一个位置。检查的是之前实际写入过的缓存，并要求前缀内容完全一致。

例如当前检查点在 block 35，单个回溯窗口大致检查 block 35 到 block 16；之前只在 block 15 写入的缓存不在这个窗口内。多个显式断点可以提供多个独立的回溯窗口，后面的断点未命中时，前面的断点仍可能启动自己的查找。

连续的 `tool_use` block 作为一个位置计算，连续的 `tool_result` block 也作为一个位置计算。因此 20 个位置不等于固定数量的 JSON 数组元素。

### 断点前移与后移

已有 block 100 的缓存时：

- 新请求把断点前移到 block 50，不能因为 block 100 的缓存存在而自动得到 block 50 的缓存；只有历史上实际写过 block 50 的缓存，才可能命中该位置。
- 新请求把断点后移到 block 200，只有 block 100 缓存仍在当前断点的 20 个位置回溯范围内，且 block 1 到 block 100 完全一致时，才可能先命中 block 100，再处理后续内容。

因此不能仅根据“新断点位置大于旧断点位置”判断一定命中。

### 前缀一致性

缓存匹配要求前缀完全一致。tools、system、messages 的顺序和内容，以及图片、工具定义和序列化结果等发生变化，都可能使前缀 key 变化。稳定内容只有在此前于某个断点实际写入过缓存时，才有机会被回溯找到。

### 关于哈希实现的边界

Anthropic 对外公开的是“以断点结束的完整前缀”及其回溯查找语义，没有公开后端是否采用增量哈希、哈希算法、零拷贝或 prefix tree 等具体实现。

因此应区分：

```text
确定：缓存 key 代表累计前缀
不确定：后端是否通过累计哈希状态计算该 key
```

工程上可以使用增量哈希降低重复扫描成本，但不能把它描述为 Anthropic 已确认的内部实现。

### 当前骨架中的累计哈希

现有请求骨架在保留 `BlkHash` 独立块哈希的同时，增加 `PrefixHash` 累计哈希数组：

```text
PrefixHash[0] = hash(参数指纹, 块0)
PrefixHash[1] = hash(参数指纹, 块0, 块1)
PrefixHash[2] = hash(参数指纹, 块0, 块1, 块2)
```

每个块的累计哈希输入包含版本标识、参数指纹、消息边界、块类型、块名称和独立块哈希。因此相同正文放在不同角色下，或者相同块分布在不同消息边界下，会产生不同的累计前缀哈希。

`PrefixHash` 与 `BlkHash` 一样按块对齐，并持久化到 `cache_skeletons.prefix_hash`。已有 ClickHouse 表会在迁移时补充该列；旧数据没有累计哈希时使用空数组，保持历史骨架记录可读取。

## 命中、创建与失效

缓存位置记录应由实际缓存结果驱动：

- cache read：提高对应位置的可信度，并刷新不超过上游实际 TTL 的有效期；
- cache write：记录可能新建的前缀位置；
- 成功但没有缓存字段：不能直接视为缓存失效；
- 未命中：先降低可信度，不立即删除；
- 连续确认未命中、已知同账号同区域同模型且超过预期 TTL：才考虑删除或过期；
- TTL 到期后应自然失效，避免依赖单次负面结果。

单次未命中可能由缓存淘汰、跨区域推理、key 或账号变化、上游路由不一致、前缀未达到最小缓存长度等原因导致，不能直接证明本机关系错误。

## 与现有 metadata 注入的关系

现有 Claude metadata 注入保持兼容的 `metadata.user_id` 结构。骨架前缀哈希适合放在其中的 `session_id` 位置，而不是把渠道 ID 拼入 session ID：

```json
{
  "device_id": "稳定的调用方或 API key 设备标识",
  "session_id": "h7"
}
```

这样同一内容前缀在渠道故障迁移或重试后仍保持相同的上游会话身份；渠道和 AWS 账号只作为本次请求的结果归因与缓存证据维度，不作为本方案的渠道选择依据。

## 实现边界

当前请求选择渠道继续使用现有逻辑。本方案只在能够确定上游请求内容后，计算或复用骨架前缀身份，并完善 `metadata.user_id` 注入：

1. 注入前骨架：从准备发送的请求中提取，用于确定可注入的最长历史前缀哈希；
2. 最终上游骨架：渠道转换、参数覆盖和重试改写完成后生成，用于诊断、缓存证据记录和校验实际发送内容。

两者可以复用底层的分块和哈希能力。若渠道转换会改变模型、system、tools 或消息内容，应以最终上游骨架为准，避免把入站请求的哈希误当成上游实际缓存前缀身份。

本方案不要求将前缀索引接入渠道选择链路，也不要求根据前缀哈希绕过现有健康检查、限流、分组和重试策略。ClickHouse 继续用于骨架诊断和结果分析；如果需要在请求之间共享注入状态，再使用 Redis 或有容量和 TTL 限制的本地缓存保存前缀身份及其缓存证据。
