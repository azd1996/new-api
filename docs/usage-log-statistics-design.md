# 使用日志统计模式方案

## 1. 背景与目标

当前使用日志页面按照时间、模型、渠道、客户、状态码、错误关键词等条件筛选日志，并以列表形式展示命中的日志条目。

新增统计模式后，用户可以在保持相同筛选条件的情况下，查看这批请求的统计结果，包括：

- 按渠道统计的多种消耗金额；
- 请求成功率；
- 状态码分布；
- TTFT、TPOT、E2E 的均值、P50、P90、P95、P99、MAX；
- 缓存命中率。

统计模式服务于消耗和错误两类日志的联合分析。它关注的是筛选结果对应的逻辑请求，而不是简单统计日志条数。

## 2. 页面形态

统计模式继续放在使用日志页面体系内，与日志列表模式并列，不复制出一套独立页面。

建议形态：

```text
使用日志
├── 公共筛选栏
├── 日志明细
└── 统计分析
```

列表模式和统计模式共享：

- 时间范围；
- 日志类型；
- 模型；
- 渠道；
- 客户；
- 用户、Token、分组；
- 请求 ID、上游请求 ID；
- 状态码；
- 错误关键词；
- 错误签名；
- Session ID、下游 Trace Tag 等已有筛选条件。

模式切换可以通过页面内的“日志明细 / 统计分析”切换完成，当前模式也应保存在 URL 中，以支持刷新、浏览器前进后退和复制链接。

不建议复制使用日志页面代码后单独维护。统计模式应复用现有筛选状态、筛选栏、权限判断和日志类型逻辑。未来如果统计功能扩展为跨时间对比、固定报表或长期趋势分析，可以再提升为独立的分析页面，但仍然复用同一套查询条件模型。

## 3. 日志类型范围

统计模式面向以下两类日志：

```text
consume + error
```

用户在使用日志筛选栏中选择“所有类型”，以便同时筛选消耗日志和错误日志。

统计模式后端不应将“所有类型”解释为数据库中的全部日志类型，而应明确限制为：

```text
type IN (consume, error)
```

系统中可能存在预扣费、重试覆盖、参数覆盖、审计等其他日志类型。它们不应混入请求数、成功率、状态码分布或性能统计。

统计模式进入时，日志类型默认设置为“所有类型”。第一版建议不允许在统计模式中切换为单一日志类型，因为成功率、状态码和请求级结果需要消耗日志与错误日志共同参与。后续如有需要，可以单独增加“错误分析”等明确限定口径的功能。

页面上可以显示：

```text
日志类型：所有类型（消耗 + 错误）
```

## 4. 时间范围

统计模式复用使用日志当前已有的时间范围控件，不新增第二套时间控件。现有控件只需要补充常用快捷范围。

建议增加：

- 今天；
- 昨天；
- 过去 1 小时；
- 过去 24 小时；
- 过去 7×24 小时。

原有的自定义日期时间范围继续保留。

各快捷范围的语义需要固定：

```text
昨天：
  昨天 00:00:00 ～ 今天 00:00:00

过去 24 小时：
  当前时间 - 24 小时 ～ 当前时间

过去 7×24 小时：
  当前时间 - 168 小时 ～ 当前时间
```

“昨天”是自然日范围，“过去 24 小时”是滚动时间范围，两者不能混用。

时间范围最终由前端转换为明确的开始和结束时间传给后端。后端只负责校验和执行查询：

- 开始时间早于结束时间；
- 范围不超过 7 天；
- 时间范围使用项目约定的业务时区；
- 必要时拒绝超出允许范围的请求。

“指定某一天”表示该业务时区下的自然日，“指定某一小时”表示该业务时区下的整点小时：

```text
指定某一天：
  当天 00:00:00 ～ 次日 00:00:00

指定某一小时：
  HH:00:00 ～ HH+1:00:00
```

建议第一版保留当前控件的自定义范围能力，并补充“今天、昨天、过去 24 小时、过去 7×24 小时”等快捷项。是否增加“最近 7 个自然日”可以在实现时根据控件空间决定，但它需要与“过去 7×24 小时”使用不同名称。

## 5. 统计对象：按 request_id 合并重试日志

new-api 自己记录 request_id，正常情况下 request_id 不会缺失。同一个下游请求在重试时会产生多条日志，常见情况是：

```text
request_id = A
  error 日志
  consume 日志
```

没有触发重试的请求通常只有一条消耗日志或一条错误日志。

因此统计不能直接按日志条数计算，而应先将日志按 request_id 聚合成逻辑请求：

```text
日志记录：
  一条 consume 或 error 日志

逻辑请求：
  同一个 request_id 下的一组 consume/error 日志
```

如果 request_id 为空，按每条日志作为独立记录处理，不能把所有空 request_id 的日志合并到同一个请求中。

### 5.1 请求级结果

第一版建议采用以下规则：

```text
请求数：
  request_id 去重后的逻辑请求数量

成功请求：
  同一个 request_id 下存在成功的 consume 日志

失败请求：
  同一个 request_id 下不存在成功 consume 日志，但存在 error 日志

成功率：
  成功请求数 / 逻辑请求总数
```

这能覆盖“先错误、后重试成功”的常见场景：

```text
error + consume
  → 逻辑请求数 1
  → 成功请求数 1
  → 失败请求数 0
```

统计状态码时，默认按请求最终结果统计，而不是把每次重试的中间状态码都当作最终结果。后续可以增加“尝试状态码分布”，用于分析渠道重试原因。

### 5.2 重试指标

重试不应污染请求数和成功率，但可以作为额外统计指标展示：

```text
重试请求数：
  同一个 request_id 下存在多条日志的逻辑请求数量

重试率：
  重试请求数 / 逻辑请求总数
```

如果一个请求发生多次重试，可以额外展示总尝试次数。按渠道统计时建议区分“逻辑请求数”和“尝试次数”，避免用户误解。

## 6. 指标口径

### 6.0 现有日志字段映射

统计模式优先使用日志列表返回的单条日志详情数据，不新增独立的详情查询。当前字段位置如下：

| 指标 | 字段路径 | 单位/说明 |
|---|---|---|
| 请求是否成功 | `log.type = LogTypeConsume` | 消耗日志表示该次尝试产生了成功消费；错误日志为 `LogTypeError` |
| 错误状态码 | `log.other.status_code` | 当前主要写入错误日志 |
| TTFT/FRT | `log.other.frt` | 毫秒；当前字段名称是 FRT，业务上作为 TTFT 使用 |
| 单次尝试 E2E | `log.other.lat` | 毫秒；缺失时可回退 `log.use_time * 1000`，但精度只有秒 |
| TPOT | 当前没有独立字段 | 需要基于现有字段推导，公式仍需确认 |
| 缓存命中 token | `log.other.cache_tokens` | 以模型访问日志当前字段为准 |
| 缓存创建 token | `log.other.cache_creation_tokens` | 以模型访问日志当前字段为准 |
| 输入 token | `log.prompt_tokens` | 数据库独立列 |
| 日志时间 | `log.created_at` | Unix 秒 |
| 请求 ID | `log.request_id` | new-api 写入并保证存在 |

缓存创建 token 还可能按 Claude 缓存 TTL 分别记录在：

```text
log.other.cache_creation_tokens_5m
log.other.cache_creation_tokens_1h
```

第一版缓存创建 token 的总数应以 `cache_creation_tokens` 为主，避免 5 分钟和 1 小时明细被重复累计。

当前成功消费日志没有确认存在统一的 `other.status_code = 200` 字段。总体成功状态可以依据同一 `request_id` 下是否存在 consume 日志判断；如果页面必须展示成功请求的明确 HTTP 状态码，需要决定是否将成功状态统一视为 200，或后续给 consume 日志补写状态码。

当前日志没有独立 TPOT 字段。不能在统计接口中未经确认地把某个推导公式当成既定口径。候选公式可以是：

```text
TPOT = (单次有效 E2E - TTFT) / completion_tokens
```

但需要先确认是否排除首 token、使用哪个耗时字段，以及 `completion_tokens = 0` 时的处理。

### 6.1 总体概览

建议展示：

- 逻辑请求数；
- 成功请求数；
- 失败请求数；
- 成功率；
- 重试请求数；
- 重试率；
- 实际日志条数；
- 统计时间范围。

“逻辑请求数”按 request_id 去重，“实际日志条数”保留原始日志数量，方便用户理解重试带来的差异。

### 6.2 按渠道的消耗金额

金额只从 consume 日志累计，错误日志不产生重复金额。

如果同一个 `request_id` 下存在多条 consume 日志，第一版将全部累计，并将该 request 标记为异常，方便在统计结果或日志中识别。正常情况下应只有一条 consume 日志；该异常不改变“全部累计”的金额口径。

建议按渠道展示：

- 逻辑请求数；
- 成功请求数；
- 失败请求数；
- 尝试次数；
- 原始消耗金额；
- 渠道折后金额；
- 客户折后金额；
- 利润。

金额口径：

```text
原始消耗金额：
  按请求原始 token/quota 计算的金额

渠道折后金额：
  应用渠道倍率或渠道折扣后的金额

客户折后金额：
  应用客户折扣后的金额

利润：
  客户折后金额 - 渠道折后金额
```

金额按实际产生 consume 日志的渠道归属。例如请求先在渠道 A 失败，再在渠道 B 成功，则错误日志不产生金额，金额归属于渠道 B。

渠道表中的“请求数”建议按逻辑请求去重，“尝试次数”按实际渠道尝试计算。这样可以同时看到渠道最终承接了多少请求，以及渠道被实际调用了多少次。

### 6.3 成功率与状态码

成功率默认按逻辑请求最终结果计算：

```text
成功率 = 成功请求数 / 逻辑请求总数
```

状态码分布也默认按请求最终结果统计。一次请求先返回 500，重试后返回 200 时：

```text
最终状态码：200
成功请求：1
失败请求：0
```

页面需要标注：

```text
成功率和状态码分布按请求最终结果统计
```

总体请求维度按整个 request_id 的最终结果统计。渠道维度需要单独按渠道尝试的最终结果统计：

```text
请求在渠道 A 失败，随后切换渠道 B 成功：

总体：
  最终状态码：200
  成功请求：1
  失败请求：0

渠道 A：
  最终状态：错误

渠道 B：
  最终状态：成功
```

因此，对某个渠道而言，即使同一 request_id 后续在其他渠道成功，该渠道本次尝试的最终状态仍然是错误。渠道成功率和渠道状态码分布不能简单复用总体请求的最终状态。

后续可以增加另一种口径：

```text
尝试状态码分布：
  统计所有实际尝试产生的状态码
```

它更适合分析 429、500、502 等错误导致的渠道重试，但不应与默认的最终请求结果混用。

### 6.4 TTFT、TPOT、E2E

每个性能指标展示：

```text
有效样本数
缺失样本数
均值
P50
P90
P95
P99
MAX
```

建议按请求级数据计算，不能因为一次请求重试产生多个性能样本。

口径和单位：

- 所有延迟使用秒；
- 保留到毫秒级，即以带小数的秒展示；
- P50、P90、P95、P99 采用与 Prometheus quantile 对照的处理方式；
- MAX 保留极端值；
- 样本数不足时仍然展示统计结果，同时展示有效样本数和缺失样本数；
- 缺失性能字段的请求只计入缺失数，不进入对应指标的分布计算。

总体请求维度：

- TTFT 使用最终有效尝试的 TTFT；
- TPOT 使用最终有效尝试的 TPOT；
- 完整请求 E2E 使用从第一次尝试开始，到最终成功或最终失败结束的总耗时；
- 计算方式为按 request_id 串联日志：第一条日志的日志时间减去该条日志耗时得到起始时间，最后一条日志的日志时间作为结束时间，两者相减得到完整 E2E；
- 重试过程中的等待时间和前置失败尝试包含在完整请求 E2E 中。

分渠道维度使用渠道尝试口径：

- TTFT、TPOT 使用该渠道尝试对应的有效值；
- 渠道 E2E 使用该渠道本次尝试的 E2E；
- 渠道 E2E 不替代总体的完整请求 E2E。

- 没有对应字段的请求不进入该指标的有效样本，但计入缺失数；
- 最终失败请求只有在错误日志存在有效性能数据时才进入对应指标。

TPOT 的具体计算公式需要结合当前日志字段确认，不能在统计实现中重新推导出与日志写入链路不一致的口径。

当前 `created_at` 只有 Unix 秒精度，同一秒内的多次重试可能无法严格排序。普通数据库可以用 `id` 作为同秒辅助顺序，但 ClickHouse 当前没有可靠的尝试序号。第一版可以按时间和可用辅助字段近似串联；如果后续要求严格处理同秒重试，需要持久化尝试序号或毫秒级尝试时间。

### 6.5 缓存命中率

缓存统计以最终有效的 consume 日志为主要来源，同时保留 token 维度和请求维度两类指标。缓存命中和缓存创建分别统计，避免把两者混成一个指标。

#### Token 维度

```text
缓存命中 token 占比 =
  缓存命中 token 数 / 总 token 数

缓存命中或创建 token 占比 =
  (缓存命中 token 数 + 缓存创建 token 数) / 总 token 数
```

其中：

- 缓存命中 token 数以模型访问日志当前记录的缓存命中 token 数为准；
- 缓存创建 token 数以模型访问日志当前记录的缓存创建 token 数为准；
- 总 token 数固定使用输入 token 总数，不包含输出 token。

#### 请求维度

```text
缓存命中请求率 =
  缓存命中请求数 / 总 unique 请求数

缓存命中或创建请求率 =
  (缓存命中请求数 + 缓存创建请求数) / 总 unique 请求数
```

请求维度按 request_id 去重。同一个请求发生重试时，只按最终有效请求的缓存结果计入一次。

第一版的请求维度使用全部 unique 请求作为分母，即使其中部分渠道或模型不支持缓存，也不从分母中排除。

建议同时展示：

- 缓存命中 token 数；
- 缓存创建 token 数；
- 输入 token 总数；
- 缓存命中请求数；
- 缓存创建请求数；
- 可判断缓存状态的 unique 请求数；
- 四种缓存比例。

第一版的四种指标按全部 unique 请求计算请求分母。本阶段不额外判断“不支持缓存”“请求不满足缓存条件”和“缓存未命中”之间的区别，页面只展示现有日志字段能够直接计算出的缓存命中 token、缓存创建 token、请求数及四种比例。

具体的“命中”和“创建”以模型访问日志当前已有的缓存命中 token、缓存创建 token 字段为准。一个请求同时存在命中 token 和创建 token 时，同时计入“命中”和“创建”两类请求，分子分别按照对应类别计算。

#### 可缓存请求的判定

本阶段不实现“可缓存请求命中率”口径。请求是否具备缓存条件与请求参数有关，目前还没有稳定的统一判定规则，因此第一版不判断请求是否满足上游缓存条件，也不计算 `cache_miss`、`cache_unsupported` 和 `cache_unknown`。

后续如果要增加该口径，需要单独设计请求参数与渠道/模型能力的判定逻辑。不能仅通过缓存命中 token 或缓存创建 token 是否大于 0 反推，因为这只能说明已经发生命中或创建，无法识别“支持缓存但本次没有命中”的请求。

## 7. 查询与数据来源

统计模式不应由前端拉取分页日志后自行汇总，也不应只依赖当前的 quota_data：

- 分页日志无法代表完整查询集合；
- 前端计算会受到数据量和浏览器资源限制；
- quota_data 适合小时级消耗聚合，无法完整支持状态码、重试、延迟分位数和缓存字段筛选。

建议新增统计接口，复用使用日志列表的筛选参数和权限规则，例如：

```text
GET /api/log/analytics
GET /api/log/self/analytics
```

接口内部统一执行：

```text
解析筛选条件
  → 限定 consume/error 类型
  → 查询日志
  → 按 request_id 聚合逻辑请求
  → 计算请求级指标
  → 计算日志级金额和尝试指标
  → 返回分模块统计结果
```

列表查询和统计查询应共用同一套后端筛选逻辑，避免相同筛选条件下两边命中不同的数据集合。

现有日志统计接口中，部分普通请求数和 quota 统计没有完全复用管理员日志列表的扩展筛选条件，而金额统计已经复用了更完整的筛选逻辑。新增统计接口时应避免延续这种差异，确保统计结果严格对应当前筛选集合。

## 8. 性能与数据库兼容性

按单日 1000 万条日志作为设计目标后，结论是：可以选择实时计算，但必须把实时计算建立在 ClickHouse 的列式聚合上，不能把日志明细拉到 Go 中处理，也不能依赖当前 `other` 文本 JSON 逐行解析。

普通数据库不适合作为这个规模下的实时统计主执行引擎。ClickHouse 可以承担单日 1000 万条、最长 7 天范围内的统计候选，但分位数、request_id 聚合和重试串联仍需要结构化字段、查询保护和实际压测。

建议的第一版实时边界：

```text
设计目标：单日 1000 万条日志
默认统计范围：24 小时
允许选择范围：最多 7 天
普通数据库：
  适合小时级或小时间范围的 count/sum/group by
  不承担 7 天全量分位数和 request_id 明细聚合
ClickHouse：
  单日 1000 万条基础统计可作为实时查询候选
  7 天基础聚合也可作为实时查询候选，但必须压测
  1000 万条以上明细不得拉入 Go 内存计算
按 request_id 查询：
  默认最多返回 1000 条日志
  硬上限 10000 条日志
```

当前数据结构下：

- `count/sum` 等只依赖结构化列的聚合，在 ClickHouse 上可以评估 7 天实时执行；
- `status_code`、`frt`、`lat`、缓存 token 位于 `other` 文本 JSON 中，不能把高频实时统计建立在对 1 亿条文本执行 `LIKE` 或逐行 JSON 解析上；
- 按 request_id 聚合需要同时限制时间范围，不能对整个日志表做无界分组；
- 均值、MAX 可以在 ClickHouse 聚合，但 P50/P90/P95/P99 应使用 ClickHouse 的近似分位数聚合或预聚合，不能拉明细到 Go；
- 完整 E2E 只适合在单个 request_id 的有限日志集合上串联，不能对 1 亿条日志逐请求在 Go 中分组；
- 如果统计要稳定支持 7 天和高并发，至少需要将状态码、TTFT、E2E、缓存 token 等统计字段列化，并评估小时级/天级预聚合。

必须通过压测确认实际延迟，不能仅凭日志条数承诺固定秒数。硬件、分片、并发、压缩率、单行 JSON 大小和查询字段都会明显影响结果。

### 8.1 单日 1000 万条的实时计算分层

在单日 1000 万条的目标下，建议将统计拆成三类：

```text
可以直接实时计算：
  总请求数、成功/失败数、金额、输入 token、缓存 token
  按渠道/状态码的基础聚合
  均值和 MAX

可以实时计算，但使用近似结果：
  P50/P90/P95/P99
  使用 ClickHouse 的近似分位数聚合

不建议每次查询扫描原始明细：
  按 request_id 去重后的完整请求级统计
  包含重试等待时间的完整 E2E
  需要严格重试顺序的渠道最终状态
```

如果“统计页面打开后几秒内返回”是硬要求，第三类指标需要在日志写入时或按分钟/小时预聚合，不能每次从 1000 万条原始日志重新拼接。可以采用以下分层：

```text
原始日志：
  详情查询、单个 request_id 下钻、问题排查

分钟/小时级统计表：
  请求数、成功/失败数、金额、token、缓存、状态码、延迟分布

实时统计接口：
  读取结构化列和统计表，按筛选条件聚合
```

因此，第一版可以提供实时统计，但应明确“实时”的实现边界：

- ClickHouse 直接聚合结构化字段；
- 分位数允许近似；
- 请求级重试串联只对单个或少量 request_id 下钻执行；
- 大范围统计不在请求过程中对 1000 万条日志逐条构造逻辑请求；
- 最终响应时间和并发上限必须通过接近生产数据量的压测确定。

### 8.2 Prometheus 是否作为统计数据源

Prometheus 可以承载预先定义好的运行指标，但不能替代使用日志统计接口，也不能解决“按照当前日志筛选条件查询历史统计”的问题。

适合写入 Prometheus 的指标包括：

```text
按固定维度的请求总量
按固定维度的成功/失败量
按固定维度的状态码计数
按固定维度的延迟 Histogram
```

这些指标适合固定的监控维度，例如：

```text
channel
model
status_code
```

但使用日志页面的筛选条件更丰富，可能包含用户、Token、客户、分组、请求 ID、错误关键词、Session ID、Trace Tag 等。若将这些字段全部作为 Prometheus label，会导致高基数问题：

- `request_id`、Session ID、Trace Tag 等几乎不能作为 label；
- 用户、Token、客户等维度组合后，时间序列数量会快速膨胀；
- 标签一旦写入，历史指标无法支持任意新的过滤组合；
- Prometheus 的 Counter、Gauge、Histogram 也无法恢复原始日志明细；
- 金额和缓存 token 等业务统计还需要保持与日志筛选集合严格一致。

因此不能采用“把所有日志转换成 Prometheus 指标，再让使用日志页面按任意条件筛选”的方案。Prometheus 的 `rate`、`increase` 和 Histogram quantile 适合监控趋势和告警，不适合作为日志页面的精确历史统计源。

推荐的职责划分是：

```text
Prometheus：
  固定维度的实时监控、趋势和告警

ClickHouse/统计预聚合表：
  使用日志页面的筛选条件
  金额、token、缓存和状态码统计
  延迟分位数
  request_id 级别分析

原始 logs：
  日志明细和单个 request_id 下钻
```

如果希望统计结果和当前日志筛选完全一致，应优先建设 ClickHouse 的统计预聚合，而不是引入 Prometheus 作为中间层。预聚合维度应根据实际使用频率选择，例如时间桶、渠道、模型、客户、用户组和状态码；高基数的 request_id、Session ID、Trace Tag 保留在原始日志中做定向查询。

如果未来需要一个独立的 Prometheus 监控看板，可以复用同一套日志写入链路额外产生固定维度指标，但这部分结果不应与使用日志页面的筛选统计混用。

### 8.3 单实例 ClickHouse 的初始查询上限

如果统计完全基于筛选命中的原始 log 实时计算，查询上限应按命中日志条数控制，而不是只按时间范围控制。单实例 ClickHouse 的实际能力取决于 CPU、内存、磁盘、分片、并发和日志字段结构，以下数值作为第一版的保守起点，最终需要用接近生产规模的数据压测修正：

```text
命中不超过 100 万条：
  允许同步计算完整统计

100 万～300 万条：
  允许查询，但页面提示数据量较大
  限制并发，必要时提高查询超时

超过 300 万条：
  不建议同步计算完整统计
  转为异步任务，或要求用户缩小筛选范围
```

上述上限针对完整统计，包括 request_id 聚合、重试处理、渠道分组、状态码、缓存 token 和延迟分位数。只做结构化列上的 `COUNT/SUM/GROUP BY` 时，ClickHouse 可能能够实时处理更大的数据量，但不能据此推断完整统计也能达到相同上限。

如果统计字段仍然从 `other` 文本 JSON 中解析，应采用更低的初始上限：

```text
同步建议上限：10 万～30 万条
```

因为此时查询需要对命中日志逐行解析 JSON，`status_code`、`frt`、`lat` 和缓存 token 的计算成本会明显高于读取独立列。将这些字段列化后，才建议把完整统计的同步上限提高到约 100 万条。

P50/P90/P95/P99 应使用 ClickHouse 近似分位数聚合，不能把全部延迟值拉到 Go 中排序。若要求精确分位数，建议把同步上限再降低，并优先使用预聚合。

统计接口还应设置：

- 单实例同时执行的统计查询数量上限；
- 单次查询扫描行数或扫描字节数上限；
- 查询超时；
- 超限时返回“请缩小筛选范围或改用异步统计”的明确提示。

因此，当前建议的产品规则是：

```text
默认：筛选命中不超过 100 万条时同步统计
警告：100 万～300 万条时允许执行但提示耗时
超限：超过 300 万条转异步或拒绝
字段未列化：同步上限先降至 10 万～30 万条
```

### 8.4 大范围统计的异步任务

如果将大范围统计改为异步任务，1 亿条日志可以在较长时间内逐步计算完成，但不能保证任意硬件环境下都有固定的完成时间。单实例 ClickHouse 能否在可接受时间内完成，取决于实际数据量、压缩后扫描字节数、磁盘吞吐、查询字段、筛选条件和业务并发。

异步任务的目标应是：

```text
允许任务慢慢完成
限制任务对在线查询的影响
任务失败后可以继续
相同查询不重复计算
```

建议采用单独的统计任务队列：

```text
等待中 → 运行中 → 分段计算 → 合并结果 → 已完成
                         ↘ 失败/可重试
```

并发控制建议：

```text
统计任务并发数：默认 1
经过压测后：最多提高到 2
同一查询条件：只允许一个运行中的任务
```

ClickHouse 查询本身还需要设置资源上限，而不能只限制应用层任务数：

- 限制单个查询使用的最大线程数；
- 限制单个查询的最大内存；
- 限制排序和 `GROUP BY` 的外部落盘行为；
- 限制单个查询最长执行时间；
- 限制可扫描的最大字节数；
- 使用独立的 ClickHouse 用户或查询 profile，和在线查询区分；
- 设置较低查询优先级，避免异步任务压过日志明细查询；
- 控制异步任务的总并发和每个用户的并发。

一个 1 亿条日志的任务不建议作为单条不可恢复的大查询执行。推荐按时间分片或按 ClickHouse 分区逐段处理，例如：

```text
按小时读取筛选日志
  → 计算该分片的结构化聚合
  → 写入任务临时结果
  → 保存 checkpoint
  → 继续下一个时间片
  → 最后合并所有分片结果
```

每个分片完成后保存：

- 任务 ID；
- 时间片范围；
- 扫描行数和扫描字节数；
- 已完成的统计结果；
- 当前 checkpoint；
- 错误信息和重试次数。

这样单个分片失败时只需要重试该分片，不需要重新扫描全部数据。任务取消后也可以保留已完成分片，后续继续执行。

需要注意，request_id 聚合和完整请求 E2E 不能简单地把每个时间片的结果直接相加。一个 request_id 的多条重试日志可能跨越时间片，因此需要：

```text
在分片结果中保留 request_id 的中间聚合状态
或先生成 request_id 级临时结果，再进行最终汇总
```

中间状态至少需要能够表达：

- 首次尝试时间；
- 最后一次尝试时间；
- 首次尝试耗时；
- 最终状态；
- 渠道尝试结果；
- consume 日志数量；
- 金额和 token 累计值。

如果异步任务仍然直接从 `other` JSON 解析统计字段，1 亿条日志的执行时间和 IO 压力会明显增加。长期方案仍应将统计字段列化，或者在日志写入时同步写入统计预聚合表。

因此，大范围异步统计可以作为第一版的兜底能力，但它适合：

```text
任务可等待数分钟甚至更久
允许单实例低并发运行
结果最终一致
按查询条件缓存结果
```

它不适合作为实时监控接口，也不能保证用户提交任务后立即得到结果。实现前需要用生产规模数据验证：单个 1 亿条任务的预计耗时、在线查询影响、磁盘读吞吐和任务失败恢复时间。

### 8.5 异步统计任务的第一版执行方式

第一版采用异步、分批和断点续跑：

```text
创建统计任务
  → 固化筛选条件和时间范围
  → 按自然小时生成待处理分片
  → 每次处理一个小时
  → 保存该小时的中间结果和 checkpoint
  → 继续下一个小时
  → 合并全部分片结果
  → 生成最终统计结果
```

任务创建时必须保存完整查询快照，不能让任务运行过程中继续读取用户当前页面的筛选状态。查询快照至少包括：

- 开始时间和结束时间；
- 生效时区；
- 日志类型范围；
- 全部筛选条件；
- 统计口径版本；
- 创建任务的用户和权限范围。

每个小时分片需要具备幂等性。重复执行同一个分片时，应覆盖该分片之前的中间结果，不能把同一分片的金额、token 或请求数重复累加。

checkpoint 至少保存：

```text
任务 ID
分片起止时间
分片状态
已扫描日志数
已扫描字节数
分片中间结果
重试次数
错误信息
```

任务状态建议包括：

```text
pending
running
paused
completed
failed
cancelled
```

任务失败时从最近一个未完成或失败的小时分片继续。任务取消时保留已经完成的分片结果，恢复任务时从 checkpoint 继续。

按小时分片时，request_id 可能跨越小时边界。因此不能只合并每个小时已经完成的最终请求结果，需要保留跨分片的 request_id 中间状态。分片边界上的请求至少需要保存：

- 首次尝试时间；
- 最后一次尝试时间；
- 首次尝试耗时；
- 最终状态；
- 每个渠道的尝试结果；
- consume 日志数量；
- 金额和 token 累计值；
- 缓存命中和创建 token；
- 性能指标有效值和缺失状态。

只有所有分片完成后，才能将这些 request_id 状态合并为最终的请求级统计。这样才能正确处理跨小时重试、完整请求 E2E、最终状态和多条 consume 异常。

任务队列第一版建议：

```text
运行中任务：最多 1 个
压测确认后：最多提高到 2 个
排队任务：限制总数
相同查询快照：复用运行中任务或已完成结果
```

异步任务结果需要绑定查询快照和口径版本。后续如果统计字段或计算口径发生变化，旧结果不能直接当作新口径结果复用。

统计查询仍需要设置保护：

- 后端强制限制最大时间范围；
- 统计查询设置独立超时；
- SQL 只查询统计所需字段；
- 金额、请求数、状态码等可由数据库完成的聚合尽量在数据库执行；
- 前端显示查询中的状态，避免重复提交相同查询；
- 对极大数据量返回明确提示。

延迟分位数需要特别考虑 SQLite、MySQL 5.7 和 PostgreSQL 9.6 的兼容性。这些数据库不能假设存在统一可用的 percentile 聚合函数。对于 1 亿条规模，不能由后端读取明细后在 Go 中统一排序计算；应使用 ClickHouse 的近似分位数能力，或提前建立小时级/天级预聚合。

## 9. 建议的接口返回结构

接口可以按统计模块组织返回结果，示意如下：

```json
{
  "scope": {
    "start": 0,
    "end": 0,
    "timezone": "Asia/Shanghai",
    "log_types": ["consume", "error"]
  },
  "overview": {
    "request_count": 0,
    "success_count": 0,
    "failure_count": 0,
    "success_rate": 0,
    "retry_request_count": 0,
    "retry_rate": 0,
    "log_count": 0
  },
  "channels": [],
  "status_codes": [],
  "latency": {
    "ttft": {},
    "tpot": {},
    "e2e": {}
  },
  "cache": {}
}
```

具体字段名称以现有 API 风格为准。金额字段应明确区分原始、渠道折后、客户折后和利润，避免前端根据字段名猜测口径。

接口同时返回原始数值和前端展示所需的格式化值：

- 金额以美元展示，最多保留 3 位小数；
- token 使用原始数值，不转换成 K/M 等缩写；
- 延迟原始值使用秒，保留毫秒级小数；
- 前端可以使用格式化值直接展示，也可以使用原始值进行排序和二次计算。

时间范围默认使用上海时区，并允许切换 UTC。接口返回实际生效的时区，前端根据该时区解释“昨天”“指定某一天”等自然时间范围。

## 10. 分阶段实施建议

### 阶段一：统计模式基础能力

- 先完成使用日志统计模式的前端界面和交互原型；
- 前端阶段使用固定假数据，不接入后端统计接口；
- 后端统计接口、异步任务队列和 ClickHouse 分片计算暂不在本阶段实现；
- 使用日志页面增加“日志明细 / 统计分析”模式切换；
- 增强现有时间控件，增加昨天、过去 24 小时等快捷范围；
- 统计模式固定使用 consume + error；
- 复用现有筛选条件；
- 新增统计接口；
- 按 request_id 合并重试日志；
- 实现总体请求数、成功率、状态码分布；
- 实现按渠道金额统计；
- 实现 TTFT、TPOT、E2E 的基础统计；
- 实现缓存命中率；
- 返回有效样本数和缺失样本数。

### 阶段二：分析增强

- 增加重试率和尝试次数分析；
- 增加最终状态码与尝试状态码两种视图；
- 增加渠道、模型、客户等维度切换；
- 增加结果排序和异常高亮；
- 增加统计结果导出；
- 评估按小时预聚合，支持更长时间范围和更高数据量。

### 当前实施边界

当前优先设计和实现前端界面。前端需要完整展示已确定的统计模块和异步任务状态，但数据全部使用本地假数据：

```text
使用日志筛选栏
  → 统计模式
  → 假数据统计结果
```

本阶段不实现：

- 后端统计 API；
- ClickHouse 查询；
- 异步任务创建、执行和断点续跑；
- 真实筛选条件对统计结果的影响；
- 真实数据量和查询耗时。

前端结构需要为后续接入真实接口保留清晰的数据边界：假数据应集中在统计 feature 的 mock 数据模块，组件通过统一的数据类型读取，后续只替换数据查询层，不重写展示组件。

## 11. 待实现前确认的问题

以下口径已经确认：

1. 总 token 数使用输入 token 总数，不包含输出 token；
2. 四种缓存指标的请求分母使用全部 unique 请求；
3. 一个请求同时存在缓存命中 token 和缓存创建 token 时，同时计入两类请求；
4. 跨渠道重试时，渠道表同时展示尝试次数和最终归属请求数；
5. 总体状态码按整个 request_id 的最终状态统计，渠道状态码按该渠道尝试的最终状态统计；
6. 总体 E2E 使用完整请求 E2E，包含重试过程；渠道维度使用本渠道尝试 E2E；
7. 延迟单位使用秒，保留到毫秒级小数；分位数采用与 Prometheus quantile 对照的处理方式；MAX 保留极端值；样本数不足时仍展示，同时展示有效样本数和缺失数；
8. 缺失性能字段的请求只计入缺失数；
